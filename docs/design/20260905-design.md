## 技術棧：零建置（使用者指定）

使用者在看過「不建議」的說明後仍選定 CDN 無 build，**這是使用者的決定，照做**。
以下是把這條路做紮實的具體方案——「無 build」與「有型別檢查、有單元測試」並不衝突。

| 面向 | 做法 |
|---|---|
| 模組 | **原生 ES modules**，`<script type="module">`。瀏覽器直接載入 `.js`，零轉譯 |
| 框架 | **Vue 3 ESM 版**（`vue.esm-browser.prod.js`，含 template compiler），用 importmap 對應裸模組名 |
| 相依取得 | **vendor 進 repo**（`vendor/vue.esm-browser.prod.js`），不在執行期打 CDN——見下方理由 |
| CSS | **手寫現代 CSS**：custom properties、nesting、`color-mix()`。不用 Tailwind Play CDN |
| 型別 | **JSDoc + `// @ts-check`**，`npx tsc --noEmit` 為選用開發期檢查。tsc **永不產出檔案**，出貨的就是那些 `.js` |
| 測試 | **`node --test`** 直接跑 `core/` 的 `.js`（node v24 原生 ESM），**測試不需要 build** |
| 部署 | 檔案原樣 push，全相對路徑 |

### 為什麼 vendor 而不是執行期打 CDN

「CDN 直接跑」的開發體驗（改完存檔、重整就看到）完全保留——差別只在 `import` 指向
`./vendor/vue.esm-browser.prod.js` 而不是 `https://unpkg.com/...`。換來的是：

- CDN 掛掉或被擋，遊戲不會整個開不起來
- 沒有第三方在執行期看得到你玩家的流量
- 版本被鎖死，不會某天上游改版就壞掉

檔案手動下載一次放進 repo，之後不用再管。**仍然沒有任何 build 步驟。**

### 為什麼不用 Tailwind Play CDN

Play CDN 是執行期 JIT 編譯器，會在 console 印「not for production」警告，且首屏要等它掃
完 DOM 才上樣式。yakyolife 的視覺是很有個性的深綠編輯感——這種需要「長得不像通用模板」
的介面，手寫 CSS custom properties 反而更快也更好控。

### 這個選擇帶來的附帶好處

沒有 bundler 改寫資源路徑，**GitHub Pages 子目錄白畫面的經典問題直接不存在**，
丟到 `YSShih.github.io/任何路徑/` 都能跑。所以「先不管部署」不會欠任何技術債。

### 唯一要留意的取捨

原生 ESM 每個模組一個 HTTP request。約 30 個模組在 HTTP/2（GitHub Pages 有支援）下
影響可忽略；若之後模組數長到 100+ 才需要考慮合檔。

## 架構

### 鐵律：`core/` 是純邏輯

零 DOM、零 `Math.random`、零 `Date.now`。必須能在 node 下單元測試、能 headless 批次跑。
**用工具強制，不靠自律**：ESLint 對 `core/**` 禁用 `Math.random` / `Date.now` /
任何 `ui` import，外加一個測試在 core 執行期間把 `Math.random` 換成 `() => { throw }`。

### 三個「事後極難補」的地基（P1 就必須做完）

#### 1. 分流 RNG — `core/rng/rng.js`

單一 mutable 隨機流是最常見的陷阱：抽卡順序一改或多插一次 `next()`，後面全部位移、
舊種子全毀。改用 **counter-based RNG**，由「主種子 + 結構化路徑字串」推導獨立子流：

```js
/** @typedef {string} RngKey */   // 'career/2027/game/03/inn/07/top/ab/02'
/** @param {number} masterSeed @param {RngKey} key @returns {Rng} */
export function makeRng(masterSeed, key) { /* cyrb128 → sfc32 */ }
```

**分流規則（寫進 CONTRIBUTING）**
- 每個隨機來源有自己的命名 key，不共用父流
- 函式間傳遞 **key 前綴字串**，不是 `Rng` 實例（實例會把消耗量耦合起來）
- 隨機迭代集合前一律 `.slice().sort(byStableId)`；禁止依賴 `Object.keys`/`Set`/`Map` 順序
- 比較機率前量化：`Math.round(p * 1e4)`

效果：**新增一張事件卡只影響該抽卡節點，舊種子的比賽逐球結果完全不變。**

種子碼用 Crockford Base32（自動修正 `I/L→1`、`O→0`，手抄或 LINE 轉貼不會壞），
`6bit version + 40bit seed + 8bit checksum → 11 字元`，顯示為 `K7QM-3XZ9-VB2`。

#### 2. 機率帳本 — `core/odds/odds.js`

「不能是黑箱」必須是架構保證，不是口頭承諾。**所有機率都經過同一個入口**：

```js
/** @typedef {{source:string, label:string, delta:number}} Modifier */  // logit 空間
/** @typedef {{base:number, modifiers:Modifier[], final:number}} Odds */
export function computeOdds(base, mods) { /* logit 相加 → sigmoid → clamp → 量化 */ }
```

UI 顯示 `62%`，展開列出玩家看得懂的中文理由：

```
基準              50%
王牌左投 vs 右打   +7
投手球數 92 球     −11
你的「用兵」42     +4
對手大心臟特質     −3
```

**Review 規則：任何寫死的 `if (rng.next() < 0.3)` 不准過；必須是
`rng.bool(computeOdds(base, mods).final)`。**

#### 3. 重播式存檔 — `core/save/`

存檔 = **種子 + 有序決策紀錄**，不存狀態快照（快照只當可丟棄的快取）。這同時解掉
generator 不可序列化的問題：

```js
/** @typedef {{
 *   formatVersion: 1, seedCode: string, engineVersion: string,
 *   contentPack: {id:string, version:string, hash:string},
 *   decisions: {seq:number, anchor:RngKey, choiceId:string}[],
 *   checksum: string
 * }} SaveFile */
```

載入 = 從種子重跑引擎，遇決策點從 log 取答案，每步驗
`prompt.rngKey === record.anchor`。不符就明確報「存檔與目前版本不相容」，
**不要靜默跑出錯誤人生**。因為決定論成立，無渲染重跑是毫秒級。

匯出走 `CompressionStream` → base64url，典型 1–3 KB，可直接貼聊天室。

**刻意不做「回到上一個決策點」** — 社群機制的價值建立在選擇不可撤回上（也才對得起
「你行你上」）。提供的是賽後**重播觀戰**，不是讀檔重骰。

**內容版本凍結**：`content/v1/` 發佈後不再修改，新內容進 `v2/`。存檔綁 pack 版本，
舊種子永遠用舊 pack 重播。不假裝內容能無限往同一個 pack 加還保證等價。

### 比賽引擎：可暫停的 generator — `core/sim/game.js`

```js
/** @returns {Generator<SimEvent, GameResult, DecisionResponse|undefined>} */
export function* simulateGame(ctx) { /* 巢狀 for：局 → 打席 → 球路，暫停就是 yield */ }
```

控制流自然，且**同一份程式碼同時服務互動模式與批次平衡測試**（headless 用 `Policy`
自動決策）。generator 實例只由 `app/store` 持有，永不進 Vue 的 reactive state。

**決策點不是每半局都問。** 用 Leverage Index 近似值挑局面，**每場硬上限 5 次**，
同時保證「王牌球數超標」「一分差第 8 局後有人上壘」這類場面必然觸發。

**能力如何進場**（每一項都必須對應玩家看得見的 modifier）：

| 來源 | 進場方式 |
|---|---|
| 球員能力 | 打者 contact/power/eye vs 投手 control/stuff/velo → 各 outcome base 機率 |
| 疲勞 | 球數在第 75/90/105 球加速拉低 control/stuff |
| 教頭·用兵 | 換投決策成功率；接手投手的手感加成 |
| 教頭·體能管理 | 疲勞累積速率 −%、受傷判定負向 modifier |
| 教頭·情蒐 | **解鎖**帶情報的決策選項（「對方代打怕內角速球」→ 佈陣 +12%） |
| 教頭·識人 | 名單建議品質；球員潛力顯示為區間而非「未知」 |
| 教頭·溝通 | 士氣 → 全隊關鍵時刻 modifier；記者會效果放大 |
| 玩家決策 | 直接改變局面（換投＝換一個 pitcher 物件） |

### 內容完全資料化 — `core/effects/apply.js`

引擎不認識任何具體卡片。事件卡、決策模板、記者會問題、球員原型都是資料：

```js
/** @typedef {
 *   | {t:'coachAttr', attr:string, delta:number}
 *   | {t:'meter', meter:'publicApproval'|'assocTrust'|'playerMorale', delta:number}
 *   | {t:'playerRating', target:CastRef, group:'bat'|'pit', key:string, delta:number}
 *   | {t:'injure', target:CastRef, weeks:[number,number], severity:1|2|3}
 *   | {t:'flag', add?:string[], remove?:string[]}
 *   | {t:'narrative', text:string}
 * } Effect */
export function applyEffects(state, fx, ctx) { /* → {state, log} */ }
```

`applyEffects` 是**唯一**能改 `CareerState` 的函式。新增 60 張卡不用碰一行引擎程式碼。
`Predicate` 用結構化 union（`{op:'gte', path, value}`）而非 eval。

卡片用「模板 + cast 選取器」（`{pick:'bestPitcher'}`、`{pick:'oldestOver', age:33}`），
一張卡套不同球員產生不同敘事——**這是控制內容量爆炸的關鍵**。

### `CareerState` 是單一 immutable 樹

Vue 元件只 emit `{type:'CHOOSE', optionId}`，只讀 computed。
`poolOrder: PlayerId[]` 是球員池唯一權威的迭代順序。

## 分階段建置

每階段結束時遊戲都**完整可玩**：能從種子碼開局 → 走完一個完整循環 → 看到結局 →
複製種子碼分享。

輸入種子碼 → 生成 40 人池 → 建議 28 人名單（可手動調）→ 打完 Premier12 賽程

**含**：零建置骨架（index.html + importmap + vendor Vue）、分流 RNG 與種子碼、

**不含**：多屆生涯、球員成長衰退、旅外徵召、記者會、協會政治、民調條、多結局。

### P2 — 「生涯」

2027 → 2028 → … 串接；球員成長／衰退／退休／新秀補進；教頭能力隱藏上限與遞減成長；

### P3 — 「中華隊題材」

旅外徵召談判（offer/counter 小遊戲，牽動忠誠度、球團限制局數、教頭溝通）；
投手用量輿論（雙向代價：操爆炎上 vs 保守被罵臕弱）；賽後記者會
（背鍋／護短／官方套話三種調性拉扯三條 meter）；協會關說與贊助商
（接受換資源／拒絕掃信任，被塞進名單的人造成戰力與士氣代價）；完整 5+ 結局。

### P4 — 「打磨與內容量」

擴充至 60+ 卡與 40+ 決策模板（引擎已凍結，純內容工作）；用 `tools/balance.js` 系統性調
`tuning.js`；生涯統計頁；鍵盤操作；丟上 GitHub Pages。

**排序理由**：P1 就把 RNG 分流、Odds 帳本、Effect 執行器、重播式存檔這四個事後極難補
的地基做完。P2 之後全部是往資料層加東西。

## 驗證方式

### 決定論（最高優先）

```js
test('same seed + same choices → identical career', () => {
  assert.equal(hashState(runScripted('K7QM-3XZ9-VB2', SCRIPT_A)),
               hashState(runScripted('K7QM-3XZ9-VB2', SCRIPT_A)));
});
```

- **Golden seeds**：3 個固定種子 + 固定決策腳本 → 快照最終 state hash 與關鍵里程碑
  （各屆名次、教頭最終能力、結局 id）。任何引擎改動動到快照就紅燈，強迫人工判斷
  「這是不是破壞了既有種子」
- **「加內容不破舊種子」測試**：測試用 pack 加一張新卡，斷言 golden 種子的**比賽逐球
  結果完全相同**（只有事件卡節點可以變）。這是驗證 RNG 分流真的有效的唯一方法
- **反 nondeterminism**：core 執行期間 stub `Math.random` / `Date.now` 使其 throw
- **存檔往返**：`import(export(s))` 深度相等；篡改 checksum 必須被拒

### 平衡（`tools/balance.js`）

```bash
node tools/balance.js games --n 1000 --matchup TPE:JPN
node tools/balance.js careers --n 1000 --policy greedy
```

- 1000 場對戰：勝率落在**區間**（vs 日本 25–40%、vs 澳洲 55–70%）；輸出平均得分、
  K/BB、HR/game、比賽長度分布。用區間避免測試脆弱
- 1000 條生涯：被解僱率 30–50%、名人堂結局 < 5%、平均任期 3–5 屆、
  **每種結局至少出現過一次**（偵測「不可能達成的結局」）、零 NaN、零無限迴圈

### 內容檢查（`tools/contentLint.js`）

- 所有 `id` 唯一；與上一版 pack 比對，**已存在 id 不得刪除或改語意**（append-only）
- `baseRate ∈ [0.05, 0.95]`；三選項卡需滿足「機率越低、Effect 幅度越大」
- 模板變數 `{{cast0.*}}` 必須有對應 `cast` 定義
- **真實球員姓名黑名單掃描** — 這個題材的法務與品味底線，用工具擋而不是靠記性

### 每階段結束的手動驗收

```bash
node --test tests/          # core 邏輯，不需 build
npx tsc --noEmit            # JSDoc 型別檢查，不產出檔案
python3 -m http.server 8080 # 開 localhost:8080 實際玩完一輪完整循環
```

（需要 http server 是因為 ES modules 有 CORS 限制，不能用 `file://` 開。
任何靜態 server 都可以，不是建置步驟。）

| 風險 | 對策 |
|---|---|
| 平衡失控 | 常數集中 `tuning.js`；P1 就建 headless harness；勝率區間護欄；Odds 帳本讓「哪個 modifier 太大」一眼可見 |

| ~~GitHub Pages 白畫面~~ | **不適用** — 無 bundler 改寫路徑，全相對路徑，丟哪個子目錄都能跑 |

# 實作過程中的偏離與發現

以上是動工前的計畫。實際實作時發現了幾件計畫沒預料到的事，記錄在這裡，
因為它們是**為什麼程式碼長這樣**的理由，而那些理由半年後最容易忘記。

## 1. 對手國家實力被重複計算（平衡）

計畫裡沒有想到：`makeOpponentSquad` 用 `nation.strength` 生成對手球員的能力值，
而 `resolvePlateAppearance` 又額外套了一次 `nationStrength` 修正——強度被算了兩遍。

**症狀**：對日本勝率只有 8.3%，遊戲的核心目標（擊敗日韓拿奧運門票）近乎不可能。

**處置**：`TUNING.atBat.nationStrength` 從 −18 降到 −6，語意改為「球員能力值以外的
隊伍素質」（守備默契、板凳深度、國際賽經驗）。

**殘餘問題與再處置**：修正後仍只有 13.3%。第二層原因是 `strength` 直接當成對手
**每一項**能力的平均值，等於日本從一到九棒、從先發到牛棚全部 82 分，比任何真實球隊
都均勻。加入壓縮係數 `50 + (strength − 50) × 0.72` 並拉大打線上下段落差之後，
對日本勝率 20%、對捷克 65%，全部護欄通過。

## 2. 「明碼機率」原本是誤導的（設計）

計畫假設「顯示成功率」就等於「誠實」。實作後用 `tools/balance.js` 量測發現：
**`greedy`（永遠選成功率最高的）表現比 `first`（永遠選第一個）還差**。
也就是說，玩家如果相信畫面上的數字去選，會被懲罰。

根因是模板違反了從 yakyolife 抄來的規則（35% 幅度最大／70% 幅度最小）：
敬遠標 62% 卻附帶白送一個跑者、觸擊標 68% 卻要送掉一個出局數。
那些結構性代價不會出現在成功率裡，所以成功率高估了選項的價值。

**處置**（兩層）：

1. 決策效果的幅度改由成功率**反向**決定：`SWING_BASE × (1 − baseRate)`。
   低機率＝大幅度，這才讓明碼成功率有意義。
2. 附帶結構性代價的選項重新定價（敬遠 0.62→0.46、觸擊 0.68→0.58），
   用成功率去反映那些成功率本身表達不了的成本。

修正後三種天真策略在 n=250 下的差距落在 1–2 個標準誤內，**沒有必勝解**，
而且亂選（random 38.4%）確實是最差的。

## 3. 第一關的難度失控（平衡）

原設計「開幕循環賽對 CZE/AUS/PAN/KOR 需 2 勝」的期望勝場只有 1.95——
**約一半玩家在第一關就被淘汰**。第一關應該是篩選不是屠殺。

**處置**：改為 5 場（加入 CHN、NED），對手整體降階但保留韓國，
讓玩家有機會在主場先把「擊敗日韓」這個門票條件存起來。第一關淘汰率降到 12.3%。

## 4.「被揃下台」原本是數學上碰不到的結局（內容）

`pickEnding` 寫了 5 種結局，但民調最壞情況只會掉到 2，永遠碰不到 `<= 0`。
`fired` 是白寫的。

計畫裡的護欄本來就是為了抓這個（「每種結局至少出現過一次」），
但我把門檻寫成「至少 3 種」，於是它放水了。

**處置**：加入 `disaster` 項（主場開幕循環賽拿不到 2 勝是災難級失敗），
並把護欄改成**列舉所有結局、逐一檢查**。現在 `fired` 出現率 12.3%。

**教訓**：護欄的門檻如果比它要保護的性質寬鬆，它就只是裝飾。

## 5. Golden 種子測試原本是假的（測試）

第一版把 `golden` 陣列拿來跟它**自己**比較，永遠不可能失敗。
已改為釘死實際數值，並用 mutation test 確認它真的會紅燈。

同樣地，`tests/purity.test.js` 的兩個掃描器第一版有誤判（掃到 JSDoc 註解裡引用的
反例字串、以及不支援跨行的 `.slice()\n.sort()` 鏈式呼叫）。已加上去註解／字串的
前處理與跨行掃描，並同樣用植入違規的方式驗證過。

**教訓**：測試與掃描器自己也要被驗證。沒被證明會失敗的測試，等於沒有測試。

## 6. 技術棧的實際偏離

- **框架**：計畫寫「不加前端框架（vanilla TS）」，使用者後續指定要用框架且零建置，
  最終為 Vue 3 ESM + importmap + vendor。
- **型別**：零建置與型別檢查並不衝突。用 JSDoc ＋ `// @ts-check`，
  `tsc --noEmit` 永不產出檔案，出貨的就是那些 `.js`。
- **Node 版本**：計畫記錄「環境 node v24.19.0」不夠精確。預設 shell 的 node 其實是
  **v12.22.12**（nvm 的 `lts/*` alias 解析到舊版），v24 有裝但沒被選中。
  v12 沒有內建 `node --test`。已加 `.nvmrc`。

## 7. 對手球員原本沒有名字

第一版播報寫成「捷克 CF 飛球出局」——那是 debug 輸出不是轉播。
加了各語系的姓氏池（`content/v1/opponentNames.js`，全部是常見姓氏，不指涉真人）。
第一版姓名池會用完並退回國名（「捷克 捷克 捷克」），已改為循環重填。

## 這些數字的兩個限制（誠實記錄）

**1. 教頭能力在 70 以上就飽和了。**
22 → 45 有 7 個百分點的提升，45 → 90 只有 1.3 個百分點。原因是目前只有 4 個決策模板、
且不是每個選項都掛教頭修正，能力的作用點太少。P4 內容擴充到 40+ 模板時應該會自然改善；
在那之前，能力點的後段邊際效益偏低是已知的。

**2. 「決策有策略深度」未經證明。**
三種天真策略在 n=250 下是 46.0 / 44.0 / 44.0，差距遠小於標準誤（約 3.1%），
彼此無法區分。這證明了**沒有必勝解**（相信畫面上的數字不會被懲罰，這是修正 #2 的目標），
但**沒有**證明「懂棒球的玩家打得比亂選好」——那需要一個情境感知的策略
（會看壘包、球數、對手打者慣性）去對照，P1 沒有做。

換句話說：目前決策提供的是**張力與參與感**，而不是可驗證的策略深度。
要驗證後者，P4 應該加一個 `POLICY_SMART` 到 `tools/balance.js`，
如果它打不贏 random，代表決策系統仍然只是裝飾。

# 邏輯稽核（2026-09-05，P1 發布後）

對 P1 做了一次完整的邏輯正確性稽核。方法是寫一支跑 400 場的稽核腳本，
逐條驗證棒球規則不變量（不會平手、出局數不超過 3、分數不倒退、
主隊領先就不打九局下、再見分後不再有打席），再用資料追蹤每個狀態欄位
到底有沒有被讀寫。以下是找到的問題與處置。

## A. 棒球規則錯誤

### A1. 沒有實作再見安打（8.5% 的比賽受影響）

九局下（含延長）主隊取得致勝分之後，程式仍然把那個半局打完三出局。
34/400 場出現這個狀況，最多的一場在超前後又多打了 4 個打席，比數被灌水。

**處置**：加入 `isWalkOff()` 判定，得分當下就中止半局並中止整場。

### A2. 延長賽平手被判為敗（2% 的比賽）

`MAX_INNINGS = 12` 打完仍平手時，`win = runsUs > runsThem` 判定為 `false`。
8/400 場以平手收場，而平手一律算輸——等於用一個永遠倒向玩家不利的規則
決定 2% 的比賽。

**處置**：加入突破僵局制（第 10 局起每個半局從一二壘有人開打），
上限放寬到 15 局。修正後 400 場零平手，延長賽也收斂得更快
（原本 10/11/12 局各 12–13 場，現在集中在 10 局 27 場）。

## B. 宣告了卻沒有作用的狀態

### B1. 傷病擲了骰、存了狀態，然後什麼都沒發生

`applyPostGame` 會擲傷病骰並寫進 `condition.injury`，`suggestRoster` 也會濾掉傷兵——
但名單在賽前就定案了，`gameSquad` 直接讀 `roster.lineup`，
所以第 3 場受傷的球員第 4 到 10 場照樣先發。

**處置**：`gameSquad` 改為排除傷兵並從板凳遞補；先發輪值改挑健康且最新鮮的；
板凳真的空了才讓人帶傷上場（國際賽名單固定，湊不出九人不是合法狀態）。

### B2. `condition.fatigue` 與 `condition.workload` 是死的

兩者都只在球員生成時被初始化，之後從沒被寫入或讀取。
型別註解卻寫著「賽會內累積」。

**處置**：實作 `workload`（投球累積、休息消化、換算成本場有效球數），
移除沒有用到的 `fatigue`。

## C. 面板承諾了引擎沒做的事（最嚴重）

這一類最嚴重，因為整個遊戲的賣點就是「不是黑箱」。

| 選項說明對玩家說的 | 稽核時的實際行為 |
|---|---|
| 續投王牌失敗「傷病風險大幅上升」 | 傷病是每場固定機率，**跟球數、跟這個決策完全無關** |
| 「士氣上升」 | `playerMorale` 在比賽中**從沒被修改過** |
| 「牛棚保留戰力」 | **沒有**跨場次的牛棚追蹤，不用牛棚沒有任何好處 |
| 「板凳完全保留」 | 板凳每場重置，「保留」跨場次沒有意義 |

**處置**：前三項改為實作（球數超過門檻會提高傷病機率、決策成敗累積士氣、
投球負荷跨場次累積且休息才會消化）；第四項改寫成實際成立的說法
（「代打留著應付後面的局面」——這在單場內是真的）。

## D. 投手調度根本是壞的

追蹤單一生涯的每場投手球數時發現：

```
第1場  林默宸:112  楊宸晉:93
第2場  江諺祐:112  陳弘冠:96
...
CP 許峻澤  pitchesInEvent 0     ← 終結者整屆一球沒投
RP 楊宸晉  pitchesInEvent 519   ← 一個人投了 8 場
```

兩個原因：

1. **牛棚順序永遠不會輪替。** `myPitcherIdx` 每場從 0 開始，換投只前進到 1，
   所以第二任投手永遠是牛棚的第一個人。牛棚深度形同不存在。
2. **換投門檻對所有投手一視同仁**（`AUTO_PULL_PITCHES = 118`）。
   後援投手也被留到破百球，而真實後援投 15–30 球。

**處置**：換投改為挑「賽會內累積球數最少」的可用投手，終結者保留到第 8 局以後；
門檻改為依角色（先發 92、後援 26）加上續航力修正。

修正後：平均每場用 5.0 個投手（真實 MLB 約 4.4），先發 99–107 球、後援 18–43 球，
7 個牛棚加終結者全部輪得到。

### 這次之後仍然存在的兩個限制

**1. 難度曲線在實力 74 以上飽和。**

# 遊玩機制調整（2026-09-05，P1 發布後第二次）

使用者要求三件事：每場比賽可以選關鍵調度、每場賽後提示結果並讓玩家設定能力、
能力設定加上自動配置。

## 動手前先量化

「每場比賽可以選關鍵調度」有兩種讀法，差別很大，所以先量測現況：

```
每場賽中決策數分布（653 場）
  0 個: 11.6%   ← 玩家整場只能看
  1 個:  0.9%
  2 個: 30.5%
  少於 3 個合計 43.0%（TUNING.decision.minPerGame 設定是 3）
```

`minPerGame` 是一個沒有在做它宣稱的事的設定。

再往下查根因，發現**不是門檻的問題**：

```
18 場零決策中
  17 場：shouldPause 有觸發（最多 39 次）但沒有任何模板命中
   1 場：shouldPause 全程沒觸發
```

原因是當時四張模板全都要求分差 ≤ 2 或 ≤ 3，比數一拉開就沒有一張對得上。
這是覆蓋率問題，不是門檻問題。修錯地方比不修更糟。

## 做了什麼

### 1. 賽前調度（新）

每場比賽前一個畫面，兩個選擇：

- **先發投手**——從健康的輪值裡挑，畫面上顯示每個人的賽會累積球數。
  這才是真正的調度張力：要不要把王牌留給日本。
- **跑壘方針**（積極／平衡／保守）——影響多推進一個壘包的成功率，
  同時影響失敗時被觸殺的機率。是變異數的取捨，不是免費加成。
  測試會斷言「積極的被觸殺次數必須高於保守」，否則就是免費加成。

方針會記住上次的選擇，所以每場只要按「確定出戰」就走。

### 2. 決策覆蓋率

- 新增兩張刻意不設分差條件的模板：`bullpen_management`（大幅領先時要不要保留戰力）
  與 `offense_tempo`（要不要動跑者）
- 新增 `STEAL` 動作，跑者會真的推進或被觸殺 —— 不是只給一個手感修正然後在敘事裡
  說「跑者上二壘」。含盜本壘
- 放寬既有模板的觸發條件

結果：零決策 11.6% → 1.8%，少於 3 個 43% → 6.2%，63.7% 的比賽達到上限 5 個。
加上每場都有的賽前調度，「整場只能看」不再發生（有測試守著）。

### 3. 賽後戰報與即時分配

每場結束後給一張結果卡（比分、本場最佳、精華、傷兵、獲得點數），
接著分配該場拿到的點數（勝 2／敗 1）。賽事結束時仍保留名次獎勵那一大筆。

勝場點數從最終結算移除，避免重複計算。

### 4. 自動配置

一鍵花完所有點數。策略是「衝最有效益的」，但實作上繞了兩圈才對：

**第一版**：按「該能力在決策模板裡被引用的權重」取最大值。
結果把 12 點全倒進用兵 —— 因為五項起始值相同，純比權重就永遠是同一項。
一維教頭實際上更弱：情蒐掛零代表佈陣選項永遠很爛。

**第二版**：加集中度遞減。仍然全倒進用兵 ——
用兵的權重是體能管理的 6 倍，1.5 倍的遞減蓋不過去。

**第三版（採用）**：改成**目標比例**。每一點都補「目前佔比距離應有佔比差最多」的能力。
但這樣體能管理永遠拿不到點數 —— 五項起始值相同（各佔 20%），
任何目標佔比低於 20% 的能力就永遠不會被選中。

**根因**：模板引用次數只反映檯面上的價值。體能管理降低全隊投手的疲勞與傷病、
識人決定潛力揭露精度，這些作用完全不透過決策模板發生。
所以改成**逐項明列的場外基準權重**（`TUNING.coach.autoAllocateBase`），
而不是一個統一底數。測試會斷言「一整屆下來每一項能力都要拿到過點數」。

### 5. 順手修掉的問題

**傷病機率套用在整份名單上**，連整場坐板凳的人都有 4% 機率受傷，
一屆下來傷掉 11 人（40% 的名單）。改為只套用在實際上場的球員，並下調基礎機率。
修正後平均 3.9 人次／屆。

**新引進又當場修掉的 bug**：跑壘方針加上「推進失敗可能被觸殺」之後，
一支安打上兩個跑者同時被觸殺，加上原本的出局數會變成 4。
三出局之後這個打席就該結束了。用 108,000 種組合驗證上限。

### 已知的取捨

**節奏變重。** 每段生涯的提示從 28 增加到 54。自動配置把賽後分配壓成一鍵、
賽前調度記住上次的方針，但這仍然是一個「每場都要停兩次」的遊戲。
如果實際玩起來覺得煩，最先該砍的是賽後分配的頻率
（改成每個階段結束才給，而不是每場）。

**奧運門票取得率從 27.3% 升到 32.0%。** 因為教頭在賽事進行中就會變強，
不再是打完才一次結算。仍在護欄範圍（10–45%）內，但這是「每場給點」的必然結果。
